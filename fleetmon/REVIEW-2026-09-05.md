# Fleetmon review — 2026-09-05

Scope: clearer dashboard, lightweight compute-node collection, fresh updates,
dedicated idle GPU view, and related correctness/usability fixes. GLM edits
through modelctl are pending explicit approval to send source/tests to z.ai;
automatic approval review rejected the first delegation. No deployment changes.

## Verified baseline

- Hub on numpi active, service memory approximately 46 MiB.
- One existing rtx3090-1 helper invocation: 40 MiB peak RSS, 0.468 s elapsed.
  This is a single measurement, not a fleet-wide benchmark.
- Default collection 60 s; overview/host browser refresh 15 s.
- JavaScript harness passes. Full Python baseline was interrupted near its end
  after progress stopped; do not claim the complete suite passed this review.
- Live overview reports process-detail truncation as `partial` on helper hosts.
- Clock skew observed: ada1 approximately 40 minutes behind hub; rtx4090
  approximately 4 minutes ahead. Freshness must distinguish hub receipt time
  from remote wall clock, and expose clock drift separately.

## Correctness fixes

1. `database.py:gpu_recent` selects GPU rows from history rather than GPU rows
   belonging to the latest consecutive host polls. Missing GPU observations
   disappear from the query instead of breaking the idle chain. Reproduced
   locally: two idle samples followed by a missing/NVML-error sample still
   produce an idle event from old GPU rows.
2. The same query omits sample-level NVML validity, timestamps, boot identity,
   GPU support and MIG status. A shared idle classifier should check these,
   distinguish normal top-process truncation from unreliable GPU telemetry,
   and treat invalid or expired readings as unknown.
3. `service.py:_notify_gpu_free_inner` retains `gpu_free_notified='sent'`
   when a GPU becomes busy. Later idle transitions can remain suppressed.
   Reset notification state on genuine busy/unknown transitions and test the
   entire busy-to-idle sequence with a fake poster.
4. `notify.py:evaluate_gpu_free` requires two evaluations of an already-idle
   pair, effectively requiring three samples on initial arrival; align with
   the documented two distinct observations.

## Dashboard fixes

- Screenshot-confirmed host meter defect: `renderHost` passes a host sample
  without GPU aggregate fields to `renderMeters`; the function treats missing
  `gpu_count` as zero and says "no GPUs" while the GPU table has three rows.
  Derive GPU summaries from the current GPU collection; distinguish missing
  telemetry from known zero devices. That meter also divides utilization by
  100 despite the stored fraction convention; use consistent units.
- Overview host sidebar is empty: `refreshSidebar` skips overview, and its
  main refresh path does not populate the sidebar. Confirmed in live browser.
- Wide overview table pushes GPU information beyond the viewport, even on
  desktop. Prioritize GPU availability and health in responsive summary/cards.
- rtx3090-2 root disk was 98.8% used in the live view without a prominent alert.
  Show disk pressure and remaining space prominently; do not delete user data.
- numpi appears `retired` because bridge roles are not telemetry targets.
  Present its hub role clearly rather than implying the machine is retired.
- rtx6000 shows `helper_missing`; existing project notes say the owner excluded
  it while offline. Preserve that exclusion and label it accurately.
- `Updated` reflects browser fetch time rather than new telemetry; label
  collection age explicitly and update ages even when network requests fail.
- Full table replacement discards sorting and focus. Preserve user choices
  and avoid full chart replacement during rapid refresh.
- `fetchJson` has no timeout; a hung request can hold `refreshInFlight` forever.
  Add bounded cancellation/recovery. Sidebar requests also need overlap guards.
- Main refresh waits for history requests via Promise.all; decouple history
  from rapid metrics updates and preserve the last good chart on errors.
- Check keyboard sorting, navigation menu state, narrow layouts, empty states,
  accessible state labels, and contrast during implementation validation.

## Screenshot-driven information hierarchy

The user's screenshot shows the host page, not a request to rearrange repository
directories. Reduce reading and visual searching through this page structure:

1. Compact host header: name, readable health state, sample age, last connection
   status. Remove the large always-visible state legend.
2. Attention strip: disk pressure, stale telemetry, collection errors or clock
   drift. Show actionable facts such as remaining disk space; avoid alarming
   labels for routine process-list truncation.
3. GPU cards before all long tables: one card per GPU with index/model,
   availability label plus icon/color, utilization bar, free/total VRAM,
   process count and current owner when available. Unknown owner stays unknown.
   Zero utilization with a resident process remains busy. Availability is an
   observation, not a reservation or guarantee against another user's launch.
4. Compact host resource strip: CPU, RAM and disk. Keep consistent units and
   bar widths; display both free space and percentage for storage.
5. History directly below the summary, using a compact responsive grid and a
   shared time-range control. Fetch history less often than current metrics.
6. Workloads: default to GPU processes and top resource consumers (about ten
   rows), searchable by user/process/PID. Explicit controls reveal more rows.
   Preserve search, sort, expansion, focus and chart range on refresh.
7. Collapsed user breakdown and diagnostics. Boot ID, helper version/path,
   observation window and truncation counters belong in diagnostics, rather
   than above the GPU information.

Global navigation: Overview, Idle GPUs, Jobs, and Hub health, followed by a
compact searchable host list. On small screens, collapse navigation and stack
GPU cards; do not require horizontal scrolling to see availability.

Idle GPUs: idle first, filters for model, host and minimum free VRAM, clear
busy/unknown counts and observation age. Fleet overview: summary counts and
host cards or compact rows emphasizing available GPUs and attention items.

Acceptance: at normal desktop zoom, host identity, warnings, all three GPUs
from the supplied example and core resource meters should be visible without
scrolling through diagnostics or process lists. Charts must precede expanded
tables. Verify narrow screens, keyboard use, refresh continuity, missing GPU
data and the screenshot's contradictory GPU count case.

## Performance approach to validate

- Independent per-target schedules so slow nodes cannot delay healthy nodes.
- Keep scheduler queries at a conservative cadence separate from direct hosts.
- Separate rapid current state from slower persisted history; increasing the
  current full-snapshot storage rate from 60 s to 2 s would multiply rows by 30.
- Lazy imports for helper startup; bounded process selection and psutil cache
  handling. Preserve GPU process visibility, user totals and truncation flags.
- Measure before/after helper RSS, CPU and latency on a canary, plus hub RAM,
  API latency and data age. Faster browser refresh alone is not realtime.
